## Smallest useful flow (core-first, judgment.md section 7)
On the Add & Evaluate tab add a "Bulk" mode: a textarea where Mike pastes many job URLs (one per line) and/or JD texts (separated by a line containing only `---`). Button "Add all". A client-side loop (JS) processes items ONE AT A TIME through the EXISTING /prefill then /job-submit endpoints, showing a live results table: row per item (URL or first 60 chars of text), status (queued / fetching / saved / failed), decision badge (Apply/Review/Skip) and score when saved, link to /job/{id}, and the failure reason for failed rows (from the endpoint error). No new backend route unless strictly needed. At the end show a summary ("7 saved, 3 failed") and an "Open Review queue" button that links to the existing /review-queue?ids=<saved job ids with decision review> (only if any), so assessment stays the existing explicit step.
Rules: cap 15 items per run (show a clear message and process the first 15); trim/skip blank lines; dedupe identical URLs within the run; validate scheme client-side (only http/https lines are treated as URLs, otherwise as text block only when using `---` separators — a line that is not a URL and not inside a `---` block is reported as "not a URL" failed row); a failed item never stops the others; a "Stop" button aborts remaining items; the textarea and results survive nothing (no persistence needed); if the index already has a job with the same source URL, mark the row "already saved" and link it instead of creating a duplicate (find how source_url is stored in src/job_hunt_index.py / reviewed job JSON; if no reliable lookup exists, note it and skip this dedupe rather than inventing one).
Escape all displayed text (URLs, errors) — no innerHTML with raw data.
Out of scope: queueing LLM assessment, server-side batch endpoint, progress persistence, CSV import.
